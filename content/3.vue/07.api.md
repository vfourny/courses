## Pourquoi appeler une API ?

Une SPA Vue interagit avec un backend via des **appels HTTP**. C'est ainsi que l'application récupère des données (cartes, utilisateurs, decks...) et envoie des modifications (création, mise à jour, suppression).

Vue ne fournit pas de client HTTP intégré. On utilise soit :
- **`fetch`** — API native du navigateur, disponible partout, sans dépendances
- **Axios** — librairie tierce, plus de fonctionnalités mais dépendance supplémentaire

Ce cours utilise **`fetch` natif** encapsulé dans un composable, ce qui est le pattern recommandé pour les projets Vue 3 modernes.

## Rappel : fetch natif

```ts
// Requête GET simple
const response = await fetch('https://api.example.com/users')
const users = await response.json()

// Requête POST avec JSON
const response = await fetch('https://api.example.com/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Alice', email: 'alice@example.com' }),
})
const newUser = await response.json()
```

`fetch` ne rejette pas la promesse en cas d'erreur HTTP (404, 500...). Il faut vérifier `response.ok` manuellement.

## Le composable useApi

Centraliser les appels HTTP dans un composable présente plusieurs avantages :
- **Un seul endroit** pour gérer le token d'authentification
- **Gestion d'erreurs uniforme** (statuts HTTP → messages lisibles)
- **URL de base** configurée via variable d'environnement

### Configuration des variables d'environnement

```sh
# .env
VITE_API_BASE_URL=http://localhost:3001/api
```

```sh
# .env.production
VITE_API_BASE_URL=https://mon-api.example.com/api
```

### Implémentation

```ts
// src/composables/useApi.ts
import { useStorage } from './useStorage'

const BASE_URL = import.meta.env.VITE_API_BASE_URL
const storage = useStorage()

const request = async <T>(
  path: string,
  options: RequestInit = {},
): Promise<T> => {
  const token = storage.get<string>('token')

  const headers: Record<string, string> = {
    'Content-Type': 'application/json',
    ...(options.headers as Record<string, string>),
  }

  if (token) {
    headers['Authorization'] = `Bearer ${token}`
  }

  const res = await fetch(`${BASE_URL}${path}`, { ...options, headers })

  if (!res.ok) {
    const data = await res.json().catch(() => ({}))
    throw new Error(
      (data as { message?: string }).message ?? `Erreur ${res.status}`,
    )
  }

  return res.json() as Promise<T>
}

export function useApi() {
  return {
    // Auth
    signIn: (credentials: { email: string; password: string }) =>
      request<AuthResponse>('/auth/sign-in', {
        method: 'POST',
        body: JSON.stringify(credentials),
      }),

    // Ressources
    getUsers: () => request<User[]>('/users'),
    getUser: (id: number) => request<User>(`/users/${id}`),
    createUser: (data: Partial<User>) =>
      request<User>('/users', {
        method: 'POST',
        body: JSON.stringify(data),
      }),
    deleteUser: (id: number) =>
      request<void>(`/users/${id}`, { method: 'DELETE' }),
  }
}
```

## Utiliser useApi dans un store Pinia

La bonne pratique est de centraliser les données récupérées depuis l'API dans un **store Pinia** — les composants consomment le store, pas l'API directement.

```ts
// src/store/users.ts
import { defineStore } from 'pinia'
import { ref } from 'vue'
import { useApi } from '@/composables/useApi'

interface User {
  id: number
  name: string
  email: string
}

export const useUsersStore = defineStore('users', () => {
  const api = useApi()
  const users = ref<User[]>([])
  const isLoading = ref<boolean>(false)
  const error = ref<string | null>(null)

  const fetchUsers = async (): Promise<void> => {
    isLoading.value = true
    error.value = null
    try {
      users.value = await api.getUsers()
    } catch (e) {
      error.value = e instanceof Error ? e.message : 'Erreur inconnue'
    } finally {
      isLoading.value = false
    }
  }

  const deleteUser = async (id: number): Promise<void> => {
    await api.deleteUser(id)
    users.value = users.value.filter((u) => u.id !== id)
  }

  return { users, isLoading, error, fetchUsers, deleteUser }
})
```

## Utiliser le store dans un composant

```vue
<template>
  <div>
    <p v-if="isLoading">Chargement...</p>
    <p v-else-if="error" style="color: red">{{ error }}</p>
    <ul v-else>
      <li v-for="user in users" :key="user.id">
        {{ user.name }}
        <NButton size="small" type="error" @click="usersStore.deleteUser(user.id)">
          Supprimer
        </NButton>
      </li>
    </ul>
  </div>
</template>

<script setup lang="ts">
import { onMounted } from 'vue'
import { storeToRefs } from 'pinia'
import { useUsersStore } from '@/store/users'

const usersStore = useUsersStore()
const { users, isLoading, error } = storeToRefs(usersStore)

onMounted(() => {
  usersStore.fetchUsers()
})
</script>
```

## Cycle de vie et appels API

`onMounted` est le hook idéal pour déclencher un appel API au chargement d'une page, car il s'exécute **après** que le composant est rendu dans le DOM.

```ts
onMounted(async () => {
  await usersStore.fetchUsers()
})
```

## Gestion des erreurs dans l'UI

```vue
<template>
  <div>
    <NAlert v-if="error" type="error" closable @close="clearError">
      {{ error }}
    </NAlert>

    <NButton :loading="isLoading" type="primary" @click="usersStore.fetchUsers()">
      Rafraîchir
    </NButton>
  </div>
</template>
```

## Architecture recommandée

```
src/
├── composables/
│   ├── useApi.ts         ← Fetch HTTP centralisé
│   └── useStorage.ts     ← Persistance localStorage
├── store/
│   ├── auth.ts           ← Authentification (token, user)
│   └── users.ts          ← Données métier
└── pages/
    └── UsersPage.vue     ← Consomme le store, pas l'API directement
```

> **Bonne pratique :** Les composants et pages ne doivent jamais appeler `useApi()` directement. Ils passent toujours par le store. Cela centralise la logique et facilite les tests.
